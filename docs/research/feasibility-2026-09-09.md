# 本地 interview-assistant 对标收费产品：可行性与增强路线

- 日期：2026-09-09（Asia/Shanghai）
- 本地基线：`57936d6aec89a6844ee9b980acff6aaba7077ceb`
- 对标样本：用户提供的 `exe/mianxiaozhu-setup.exe`；官网资料采集于 2026-09-08。
- 本轮范围：可行性评估和方案，不实现功能，不安装或执行对方软件，不调用真实模型接口。
- 证据口径：**已观察**＝本地源码/安装包静态结果；**推断**＝基于证据的判断；**提案**＝待开发与验证，不是已经具备的能力。

## 1. 结论

**建议做，而且建议在现有项目上增量增强，不推倒重写。**

分开看三个目标：

| 目标 | 判断 | 限制 |
| --- | --- | --- |
| 补齐对标样本可见的主要客户端功能 | 技术可行性高 | 模拟面试、可选混合检索、异步翻译和成品打包都能纳入现有架构；需要独立实现及测试 |
| 在部分维度超过对标产品 | 有合理路径 | 先选模拟面试反馈、个人知识引用、学习闭环、可靠性与透明度；结果必须靠实测，不能只靠功能数量 |
| 复刻完整收费运营产品 | 不是同一个工作量 | 还包含未获得的远程服务、模型供应、账号、支付、风控、运维和授权；不建议首期做 |

这些是工程判断，不是开发周期承诺。当前证据不足以声称我们已经更好，也不足以断言对方没有服务端技术积累。[S1][S2]

**推荐的第一版定位：Windows 本地优先、免强制账号、用户自配 API（BYOK）的面试练习与复盘工作台。** 首期以学习、模拟面试和经允许的辅助场景为目标；不把规避监考或绕过他人监控作为增强方向。是否提供商业服务是另一个决策。

## 2. 对“对方是在开源项目上二开收费”的判断

本地静态比较范围为后端 Python 文件，排除 tests/scripts/__pycache__。两个对象有 74 个共同相对路径，其中 39 个文件原始字节完全相同；大于等于 200 bytes 的共同文件中，32 个经过 BOM/CRLF 归一化后相同。[S3]

因此，**存在共同代码基础的猜测有技术证据支持**。但以下结论不能从相似性直接推出：

- 谁先复制谁、具体基于哪个版本；
- 是否同一作者、同一团队或已取得额外授权；
- 是否侵权、商业化是否合法；
- 整个产品有某个百分比“抄袭”。

增强项目时，使用本仓库许可允许复用的源码；从对标分析中提炼功能需求，**不把安装包新增源码、私有提示词、界面素材、密钥或服务端地址直接搬进我们的实现**。独立重写对标新增功能也不自动消除现有仓库本身的许可证限制。

## 3. 许可是商业化的前置条件，不是本地技术实验的障碍

本地 `LICENSE` 为 CC BY-NC 4.0，允许依约分享和改编，并附带署名、修改说明及非商业条件。[S4] CC 官方条款中的非商业限制不能理解为 MIT/Apache 式的任意商业复用。[W1]

- 可以在符合许可条件的前提下研究和增强项目；具体使用是否属于非商业需要按实际场景判断。
- 如果计划销售客户端、开展收费托管或商业分发，先确认权利人与额外商业授权范围；不能拿“对方也收费”作为我们的授权依据。
- 依赖库、模型权重、图标字体等还可能有各自的许可，应纳入第三方清单。
- 未取得授权时，不把现有改版直接规划成可售卖产品；即便独立重写，也应单独审查代码来源和权利边界。

本节仅是许可风险提示，不对具体主体作法律结论。

## 4. 为什么现有架构足够支撑增强

已有技术分层是 React/TypeScript/Vite + Electron + Python/FastAPI，通过 HTTP/WebSocket 连接，已有 ASR、流式 LLM、截图识题、知识库、复盘、简历优化及求职管理。[S1][S5][S6][S7]

对标样本也采用 Electron + React 构建前端 + 内置 Python/FastAPI，并有模拟面试、翻译、账号/远程代理及 Chroma 相关新增实现。这说明可见差距主要落在应用层和交付层；**并不能证明两者使用相同远端模型，或具有相同效果**。[S2]

建议保持：

```text
Electron：启动、关闭、更新、权限与受控 IPC
  └─ React：现有工作台 + 新模拟面试 + 引导/诊断/隐私面板
       └─ 本地 FastAPI
            ├─ 既有实时流水线（小步加固，不整体翻写）
            ├─ 新模拟面试领域（独立会话状态机）
            ├─ 检索接口（原有 BM25 + 可选语义检索）
            ├─ 模型/语音适配器（自配服务；本地引擎可选）
            └─ 存储（SQLite、附件目录、独立密钥管理）
```

暂不引入微服务、Redis、消息中间件和 Kubernetes；也不为了“技术升级”立即换掉 Electron 或 FastAPI。这是控制迁移面和回归风险的提案，不是断言这些替代方案不好。

### 5.1 模拟面试：最值得优先补齐的独立功能

建议第一条纵向链路：

```text
岗位/JD/简历选择 → 本次资料快照 → 面试计划
 → 提问 → 文字/语音作答 → 基于回答的追问
 → 分维度点评 + 回答原文证据 + 参考改进
 → 总结报告 → 弱项练习 → 再次复测
```

关键设计提案：

1. 会话状态独立于现有实时辅助全局状态，至少区分进行中、等待模型、完成和失败/可恢复。
2. 题目、回答和点评具备稳定 ID；请求重复提交应幂等；取消后不能把迟到结果写进下一题。
3. 固定本场简历/JD/题目配置快照；不得把后续修改的资料冒充本场使用的输入。
4. 评分按事实正确性、结构、岗位相关性等 rubric 输出；附回答原文证据，显示 AI 判断的局限。
5. LLM 输出有 schema 校验、失败恢复及回退路径；不能只凭自由文本中提取一个分数。
6. 无依据时明确资料未提供，不编造个人经历；参考答案与“用户实际回答”分开保存。
7. 先交付文字版的可恢复完整闭环，再接语音录制/转写；不把实时全双工语音作为首个版本前置项。

### 5.2 知识库：对标检索能力，不机械照搬 Chroma

原有关键词检索已经实现 deadline 控制，增强时保留它。[S10]

提案是把语义检索做成可选适配器，合并 BM25 与语义结果，并保留来源、去重和时间预算。是否使用 Chroma、是否加重排，应由我们的资料量、包体与评测结果决定；安装更多组件不等于回答更准。

还需处理：索引增量更新、删除一致性、Embedding 模型/维度版本、模型切换后的重建、重启恢复和备份。使用远端 Embedding 会发送文本，必须纳入明确的数据流说明；不能把“向量库落本地”宣传成“资料没有出本机”。

### 5.3 安装包：不能只加一个打包命令

electron-builder 文档提供额外资源打包与 Windows NSIS 安装器配置，可以作为候选工具。[W2] 但本项目还要实际完成：

- 随包交付经过测试的 Python 运行时/依赖和前端构建物，不让最终用户首次启动再运行 npm/pip 安装。
- 将用户数据从源码/安装资源路径中分离出来；当前存储工具主要写入 `backend/data/`。[S12]
- 处理后端启动超时、端口冲突、进程退出、应用关闭、日志轮转及升级迁移。
- 本地 Whisper 权重按需安装并校验；是否随包携带应独立决策，不能假定每台机器都能流畅运行。
- 在无开发环境的干净 Windows 虚拟机上验证；对外发行前补签名、更新来源验证和回滚方案。

### 5.4 安全与隐私：属于质量门槛，不是营销词

静态源码表明，部分语音服务凭据由配置 payload 返回设置端，LAN 鉴权可配置关闭；这不单独证明已可被利用，但说明要在产品化前审查密钥、访问控制和浏览器边界。[S13]

已有 Electron 窗口设置了 context isolation 和禁用 Node integration；仍需要按官方安全清单审查 IPC 发送者、导航、内容策略及依赖维护，而不是看到两个开关就宣布安全。[S8][W3]

密钥可评估采用操作系统保护的存储接口；Electron safeStorage 的平台行为不同，不能用它的存在证明所有数据已加密，更不能保证对同用户权限的恶意进程安全。[W4] 桌面和浏览器模式应分别设计访问路径，避免 renderer 直接取得不必要的长期密钥。

## 6. “超过”必须事先定义比较方法

目前尚未运行对标软件，没有它的延迟、质量、可靠性、耗用成本和真实服务模型基线。因此现阶段只能说有超越路径，不能给“已经领先”的结论。[S2]

建议建立两类评测，禁止混为一谈：

- **产品使用效果评测**：各自的真实可用配置；记录价格、模型、设备、网络及模式，允许承认我们的自配 API 多了一步配置。
- **工程效果评测**：能控制时固定相同模型和输入，比较调度、上下文、检索、稳定性；对方不支持等同配置时标为不可控因素，不伪装成公平同条件实验。

建议验收门槛（均是未来目标，非当前实测结果）：

| 维度 | 测量方法/门槛提案 |
| --- | --- |
| 安装可用性 | 干净 Windows 11 x64、无 Python/Node；完成安装、首次配置、练习和卸载；拒绝音频权限时能正常退回文字模式 |
| 生命周期 | 连续 20 次启动/退出无孤儿后端；端口冲突、启动失败给出明确可恢复提示 |
| 会话可靠性 | 使用预制测试音频和假模型完成 60 分钟测试；已确认最终转录不丢失，过期回答不串会话；断连后恢复行为可验证 |
| 模拟面试 | 覆盖至少 50 个自动化会话场景：刷新、取消、超时、重复提交、异常 JSON、重新进入；状态和落盘结果正确 |
| 回答质量 | 使用获授权/合成资料建立至少 100 道固定评测题；盲评事实性、个人经历忠实度、岗位相关性；报告评分分布与分歧，不只展示精选好例子 |
| 检索收益 | 留出测试集比较 Recall@k/nDCG@k、引用正确率和 p95 延迟；无可复现收益时不默认开启语义链路 |
| 延迟 | 分开统计说话结束→转录确认、转录→回答首字及完整回答；固定配置下 p50/p95，先立基线再定提升目标 |
| 隐私承诺 | 使用合成密钥检查日志/导出；本地模式出网行为经过独立观测；云端模式可说明发了什么、发给谁 |
| 数据迁移 | 旧配置/旧 SQLite 可升级，升级失败可恢复；导出、删除和附件清理有回归测试 |

没有对方动态基线时，先宣称“达到我们的验收标准”，不宣称“比对方快多少/强多少”。需要真实测试软件、录音或付费接口时，再单独确认授权、隔离环境及预算。

## 7. 路线与工作量估计

假设：**1 名熟悉 React、Python 和 Electron 的工程师全职，使用 AI 辅助；Windows 11 x64 优先，BYOK，不做支付/多租户后台；估算包含开发、测试和集成。** 第三方账号/证书办理、真实用户测试排期、macOS 音频兼容和托管服务运维不在此估算内。

| 阶段 | 交付物与结束条件 | 初步人日 |
| --- | --- | ---: |
| P0 基线与边界 | 可复现依赖、完整构建/测试基线；数据和密钥路径盘点；假模型评测入口；记录未通过项 | 3–5 |
| P1 可安装的本地版 | 自包含 Windows 测试安装包、数据目录、启动诊断与首次配置；干净机完成现有流程 | 5–8 |
| P2 模拟面试闭环 | 文字核心→语音接入；计划/提问/回答/点评/报告/恢复及对应自动化测试 | 8–12 |
| P3 检索与翻译 | 可选混合检索、引用、索引版本/降级；异步双语输出；对既有流程无明显回归 | 7–12 |
| P4 差异化与加固 | 弱项练习→复测、质量评测、长会话/数据迁移/发布加固；明确公开承诺边界 | 8–15 |
| **基础合计** | P0–P4 | **31–52** |

建议另预留约 30% 不确定性缓冲：

- **第一版可安装并具备模拟面试闭环**：P0–P2，约 21–33 人日（约 4–7 个全职工作周）。
- **覆盖主要可见差异并争取在选定维度领先**：P0–P4，约 40–68 人日（约 8–14 个全职工作周）。

这是尚未建立完整运行基线时的粗估，不是报价或承诺；P0 结束后必须重估。不要把“生成几份代码的时间”等同于可发布产品的交付时间。并行开发可以缩短部分工期，但共享的音频/实时状态、数据迁移和验收不会线性加速。

## 8. 主要风险与控制方式

1. **实时链路回归**：`pipeline.py` 1933 行、`answer_worker.py` 1270 行、`desktop/main.js` 1260 行。本轮按文本行数复核；文件大不是故障证据，但提醒我们先补契约/回放测试，再围绕明确问题小步拆分，不做全局重写。[S14]
2. **测试存在不等于已通过**：仓库有后端测试、前端单测、桌面测试和 E2E/CI；当前本机完整依赖和全量测试尚未验证。CI 的后端测试命令是显式选择的文件列表，不能推断它覆盖了所有后端用例。[S9]
3. **音频兼容性**：现有实时语音能力可以复用，但系统声、麦克风、设备切换和权限必须实机测；首期限制平台矩阵，macOS 后置。[S1]
4. **效果上限受模型影响**：独立实现相同交互不代表能复现对方远端模型效果；应记录模型和配置，避免仅靠调整提示词作保证。
5. **混合检索复杂度**：新增向量依赖会引入模型下载/调用、索引版本和打包工作；必须可关闭、可降级，并通过资料集评测。
6. **隐私与信任**：对方宣传未独立验证；我们不能照抄。先完成实际数据流、密钥、诊断日志和网络测试，再写承诺。
7. **许可和供应链**：商业授权、第三方许可、依赖版本与分发来源核验均有独立工作量。

## 9. 成本与产品选择

推荐本地 BYOK 并不代表免费推理：

```text
使用成本 = LLM 输入/输出 token 成本
         + ASR 分钟成本
         + Embedding / 翻译 / Vision 成本
         + 可选本地硬件、电力、模型下载与维护成本
```

不在这里猜测具体供应商单价。官方托管服务“开箱即用”的便利，不能用“用户自己填 API”完全等价替代；如果未来要提供同样便利，需要另建受授权的模型代理及可靠的服务端产品。

首期省掉账号、会员和计时，不是因为它们不能做，而是因为它们不直接提高练习质量，又会引入运营和安全成本。后续如果确实需要商业模式，应另立授权/服务端项目，而非在客户端里硬编码服务端凭据。
